## 二、已修复

### P0-1　`AuthInterceptor` ThreadLocal 泄漏 → 认证绕过

**位置**：`user-center/src/main/java/com/example/usercenter/interceptor/AuthInterceptor.java`

**成因**：`preHandle` 第 64 行在**鉴权之前**就 `UserContext.set(...)`；当第 78 行判定
「需要管理员但角色不符」而 `return false` 时，Spring 的 `HandlerExecutionChain.applyPreHandle`
会调用 `triggerAfterCompletion`，但它只回溯到**上一个执行成功的拦截器**
（`interceptorIndex` 在 `preHandle` 返回 true 之后才推进，不包含本拦截器自身），
因此本拦截器的 `afterCompletion`（`UserContext.clear()`）**不会执行**。

**影响范围**：Tomcat 线程复用后，下一个请求（即使**不带 token**）会继承上一请求残留的登录身份。
叠加 `UserController#closeAccount` / `#changePassword` 既无 `@LoginRequired`、
又只用 `UserContext.get()` 取当前用户（`request` 参数形同虚设），
匿名请求可能以他人身份执行注销 / 改密 → **账户接管**。

**最小修复**：
1. `preHandle` 开头无条件 `UserContext.clear()`（根治：本请求的身份只能来自本请求的 token）；
2. 两处 `return false` 前显式再清一次。

**验证**：普通用户访问 `GET /resource/manage/list` → `40101 无权限`；
随后连续 30 次**匿名** `POST /user/changePassword` **全部**返回「请先登录」——0 次泄漏。

### P0-2　`createNote` 未校验 `starId` → 多租户写入越权

**位置**：`service/impl/NoteServiceImpl.java`（`createNote`）

**成因**：`createNote(@RequestBody Note note, ...)` 的 `starId` 直接来自请求体，
服务端只设置 `authorId`，从不校验「当前用户是该星球成员」。
`TenantInterceptor` 只负责查询侧的租户条件注入，对插入无约束。

**影响范围**：任意登录用户可把笔记写入**任何星球**（包括未加入的、付费的），击穿多租户写入隔离。

**最小修复**：注入 `StarMemberMapper`，当 `note.getStarId() != null` 时校验
`star_member(star_id, user_id)` 存在，否则抛 `NO_AUTH`。

> ⚠️ 注意：**不能**简单改成 `note.setStarId(UserContext.getStarScope())`。
> 前端 `NotePublish` 页不在 `router.js` 的 `ROUTE_STAR_PARAM` 中，不带 `X-Star-Id` 头，
> 是走请求体传 `starId` 的；那样改会让「在星球内发帖」功能直接失效。

### P0-3　资源审核绕过（Mass Assignment）

**位置**：`service/impl/ResourceServiceImpl.java:156`

**成因**：原实现为
```java
resource.setStatus(StringUtils.isBlank(resource.getStatus()) ? "pending" : resource.getStatus());
```
状态非空时**直接采纳客户端传入值**。配合 `/resource/add` 用 `@RequestBody Resource` 领域对象接收，
调用方传 `status: "enabled"` 即可自行上架。

**影响范围**：任意登录用户绕过 `pending → enabled` 审核流程，内容直接进入公开列表与 ES 索引。

**最小修复**：`resource.setStatus("pending")` 强制写死，忽略入参。

**验证**：带 `status: "enabled"` 调用 `/resource/add` → 落库 `status = pending` ✅

### P0-4　AI 会话越权

**位置**：`service/impl/ChatServiceImpl.java`（`resolveSessionId`）

**成因**：客户端传入 `sessionId` 时**直接 `return sid`**，不校验归属。
同文件的 `getSession(sid, userId)`（含归属校验）与 `getMessageList`（调用了该校验）都是对的，
**只有写路径漏了**。

**影响范围**：携带他人 `sessionId` 调 `/chat/message` 或 `/chat/message/stream`，
即可向对方会话写入消息，并借助以 `sessionId` 为 key 的 AI 记忆（`ChatMemory`）
读取对方**完整对话上下文**。

**最小修复**：`resolveSessionId` 中 `getSession(sid, userId) == null` → 抛 `NO_AUTH`。

### P1-1　笔记状态机绕过 + 发布积分可无限刷

**位置**：`service/impl/NoteServiceImpl.java`（`updateNote` / `publishSideEffects`）

**成因**（两个叠加）：
1. 状态校验**只拦 `rejected → published`**，没拦 `pending → published`。
   举报功能会通过 `markNotePending()` 把笔记置为 `pending`，
   于是**作者可以一键把被举报的笔记改回 `published`**，审核形同虚设。
2. `publishSideEffects()` 的注释写着「仅首次发布」，
   但代码**没有任何幂等判断**——`becamePublished` 只看 `previousStatus` 是否为 `published`，
   所以 `published → draft → published` 可以**无限重复**发放 +20 积分、
   重复 `star.content_count + 1`。

**影响范围**：审核被绕过；积分与星球内容计数被刷高。

**最小修复**：
1. 非管理员禁止 `pending → published/scheduled`；
2. `becamePublished` 增加幂等条件：新增 `hasAwardedPublishPoints(noteId)`
   查 `points_log` 是否已有 `type=publish / ref_type=note / ref_id=?` 记录，
   条件改为 `(draft || scheduled) && !hasAwardedPublishPoints(...)`。

**验证**：
- `pending` 笔记由作者改 `published` → `40101 笔记正在审核中，不能直接发布` ✅
- 正常编辑（不带 status）→ 成功 ✅（**未误伤既有功能**）
- 草稿首次发布 → 正常发放 20 积分 ✅
- 再执行 3 轮 `published ↔ draft` → `points_log` 中该笔记的 `publish` 记录**恰好 1 条** ✅

### P1-2　举报被「忽略」后笔记永久 `pending`

**位置**：`service/impl/ReportServiceImpl.java`（`handle`）

**成因**：`handle` 只更新 `report` 行的状态/处理人/备注，**不联动笔记状态**。
笔记被举报时已 `markNotePending` 成 `pending`，管理员点「忽略」后它仍停在 `pending`
（对普通用户不可见）；而作者又已无法自行改回（见 P1-1 的拦截）。

**影响范围**：被误举报的正常内容**永久消失**，只能人工改库。

**最小修复**：`status == "ignored"` 且 `targetType == "note"` 时调用 `noteService.approveNote(targetId)`
（`approveNote` 已处理副作用补发且不重复发积分）。

### P1-3　评论计数只增不减

**位置**：`service/impl/CommentServiceImpl.java`（`replyComment` / `deleteComment`）

**成因**：
- `replyComment` 保存回复后**没有**调用 `noteService.asyncIncrementCommentCount`（只有 `addComment` 调了）
  → 回复不计入 `note.comment_count`；
- `deleteComment`（含级联删除回复）**从不递减** `comment_count`，全仓无递减逻辑。

**影响范围**：`note.comment_count` 长期失真——回复漏计、删除后虚高。

**最小修复**：
- `replyComment` 保存成功后补 `noteService.asyncIncrementCommentCount(noteId)`；
- `deleteComment` 中先统计级联回复数，删除后调用新增的
  `NoteMapper.decrementCommentCount(id, delta)`（用 `GREATEST(comment_count - delta, 0)` 防负）。

**验证**：新增评论 → `comment_count = 1`；删除该评论 → `comment_count = 0` ✅

### P1-4　前端 401 后登录态不一致

**位置**：`demo1/src/utils/request.js` + `demo1/src/router/router.js`

**成因**：401 处理只调用 `clearAuthStorage()` 清 localStorage，**Pinia 内存态 `isLogin` 仍为 `true`**。
路由守卫以 `userStore.isLogin` 判定登录态，于是把 `router.replace('/login')` 又弹回首页 →
用户界面显示「已登录」却已无 token，后续请求继续 401。

**影响范围**：登录过期后无法回到登录页，表现为「反复跳转 / 卡住」。

**最小修复**：守卫中 `isAuthenticated` 改为
`!!userStore.isLogin && (localStorage.getItem('userLogin') || localStorage.getItem('token'))`。

### P2　前端二进制定响应必抛「不符合 BaseResponse 契约」

**位置**：`demo1/src/utils/request.js:42`

**成因**：响应拦截器对**所有**响应执行 `normalizeBaseResponse(response.data)`，
而该函数要求 `typeof payload.code === 'number'`；`responseType: 'blob'` 的响应没有 `.code` → 必然抛错。

**影响范围**：`api.js` 的 `downloadResource` 一旦被调用即失败。
> 实际影响面较小：该函数目前**没有任何调用方**（死代码）。

**最小修复**：拦截器开头判断 `response.config?.responseType === 'blob' || response.data instanceof Blob`
时直接 `return response`。

## 四、复核后**排除**的疑点（子代理误判，未做改动）

| 结论 | 复核结果 |
|------|----------|
| 「`application-dev.yml` / `application-prod.yml` 密钥硬编码入库」 | **误判**。二者已在 `user-center/.gitignore:38-39` 中且**未入库**；已入库的只有 `application.yml` 与 `.example` 模板。密钥治理的紧迫性远低于该结论 |
| 「`ROUTE_STAR_PARAM` 存在漏登记页面」 | **路径参数口径无漏登**（只有 `UserStarDetail`、`UserKnowledgeMap` 两个带路径参数的星球页，且都已登记）。真实隐患是 `?starId=` 形式的入星跳转（`StarDetail.vue:272` → `/user/publish?starId=`）未纳入作用域 |
| 「`/resource/upload` 无扩展名白名单 → 存储型 XSS」「SSRF」 | 属**真实的设计风险**，但利用链未验证、且取决于 OSS 与预览接口的实际暴露方式，本次未改动（见第五节） |
| 「MD5 弱哈希」 | 确实存在 `SALT = "yiyi"` 的 MD5 兼容分支（`UserServiceImpl:76`），但登录成功后会自动升级为 BCrypt，属**历史遗留兼容**，非本次引入 |
| 「`OAuthController` 无 `state` 校验」 | **部分误判**。前端 `utils/oauth.js` 早已实现随机 state（存入 sessionStorage）并在 `OAuthCallback.vue` 校验，**GitHub 分支是有 CSRF 防护的**；真正缺失的是 **QQ 分支**（后端硬编码 `state=qq_login`、回调页显式跳过），且回调页条件 `state && ...` 使「不带 state」也能绕过。这两点已在第五节第 3 项修复 |
| 「评论举报未落 `report` 表」 | 该结论来自上一轮审计的读码遗漏，实际 `CommentServiceImpl.reportComment` 末尾已落库 |
